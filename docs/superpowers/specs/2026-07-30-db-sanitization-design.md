## Требования из задания (сжато)

- Вход: дамп или подключение к БД; выход: обезличенная версия, пригодная к передаче за прод-контур.
- СУБД на выбор — **PostgreSQL**.
- Замены **правдоподобные**, для их генерации **обязательна LLM**.
- Замены **сквозные**: одно исходное значение → одно и то же новое во всех таблицах и полях.
- Сохранить: ссылочную целостность (FK), количество строк, разнообразие значений.
- Максимально использовать готовый open-source; агентский слой — поверх готового агентского фреймворка, не свой.
- Регулярная эксплуатация командой ~200 человек: воспроизводимость, автоматизируемость, надёжность.
- Большие объёмы без деградации; расширяемость на другие форматы документов без переписывания ядра.
- Сдача: репозиторий с инструкцией либо стенд + сопроводительное описание, желательно демонстрация «до/после».

## Принятые решения

| Вопрос | Решение |
|---|---|
| Стек | Гибрид: ядро и хосты на **C#/.NET**, агентский слой — отдельный **Python**-сервис |
| Агентский фреймворк | **LangGraph** |
| LLM | **Облачные API с выбором провайдера**: Claude, OpenAI, DeepSeek, GLM, Cursor — через **LiteLLM** |
| Роль агентов | **Только генерация пулов фейковых значений** (ФИО, адреса и подобное). Ничего больше |
| Обработка данных | Restore дампа в одноразовую sandbox-БД → пересборка таблиц через SQL → `pg_dump` |
| Формат сдачи | **Web-сервис** + `docker compose` для быстрого старта |
| Определение чувствительных колонок | Детерминированные детекторы предлагают, **человек подтверждает в UI**. Без LLM |
| Стабильность подстановок | Сквозная и **между запусками**: то же значение → то же новое при том же **seed** |
| Seed | Явный вход задачи: передаётся пользователем либо генерируется, если не указан. **Печатается в отчёте** |
| Механизм подстановки | **Чистая функция** от `(seed, оригинал)`. Хранимой таблицы соответствий нет |
| Механизм привязки | **Перестановка домена (FPE)** там, где алфавит фиксирован; **адресация пула хэшем** там, где нужна правдоподобность. Ранг в наборе `DISTINCT` не используется нигде |
| Размер домена пула | **Параметр замороженного плана**, не выводится из числа строк |
| Уникальные колонки | Пуловое значение + **детерминированный суффикс**; включается на семантический тип автоматически |
| Входы задачи | `seed` и **ширина суффикса** — оба печатаются в отчёте |
| Email / login | **Связный**: локальная часть от фейкового ФИО + суффикс; домен — неотправляемый `@mail.invalid` |
| FK на натуральных ключах | **Drop FK → Apply → recreate FK**; пересоздание играет роль проверки целостности |
| `json` / `jsonb` | По умолчанию **целиком** через `Redact` с сохранением структуры; разметка отдельных путей — опция ревью |
| Свободный текст | Regex-паттерны заменяются теми же функциями; `Redact` — выбор в ревью |
| Генератор текста | Подстроки **рассказа, приложенного к репозиторию**. Без LLM, длина сохраняется |
| Граница .NET / SQL | .NET строит **материалы** (пулы, рассказ, шаблоны) один раз на задачу; SQL на строку **адресует и склеивает**, но правдоподобных строк не изобретает |
| Apply | `CREATE TABLE … AS SELECT` + подмена для любой таблицы с размеченными колонками. `UPDATE` не используется |
| Пул | **Фризится вместе с планом** по хэшу; кэш в `pg-meta`, повторный прогон к LLM не обращается |
| Настройки sandbox | `fsync=off`, `synchronous_commit=off`, `full_page_writes=off`, `wal_level=minimal` — БД одноразовая |
| Расширяемость | Формат живёт только в `ISourceAdapter` / `ISinkAdapter`; ядро работает с таблицами sandbox и форматов не знает |
| Живая БД как источник | Поддерживается **адаптером, который сам снимает дамп**. В источник не пишем никогда, доступ — read-only роль, желательно реплика |

## Секция 1. Ключевая идея и конвейер

Разделяем «умное» и «тяжёлое». LLM не участвует в обработке строк: она наполняет пулы значений,
а применяет их СУБД по правилам, которые сгенерировало .NET-ядро (граница — в секции 4).

Обоснование:

- **воспроизводимость** — тот же план и те же входы задачи дают тот же результат;
- **стоимость** — обращений к LLM ~O(число семантических типов), а не O(число строк);
- **аудит** — за «что мы обезличили» отвечает версионированный план, а не промпт.

Конвейер задачи:

```
1 Ingest      дамп ─► restore в pg-sandbox
2 Introspect  схема + профиль ─► кандидаты (детерминированные правила, без LLM)
3 Review UI   человек: подтвердил / поправил / добавил / исключил
4 Freeze      plan.json + версия и хэш (в git и в pg-meta)
5 Enrich      воркер ─► Value Pool Service (агент, LLM) ─► пулы значений
6 Apply       правила ─► пересборка таблиц в sandbox (CTAS + подмена)
7 Verify      проверки целостности/объёма/разнообразия ─► pg_dump ─► отчёт
```

Шаги 1–4 интерактивные, 5–7 — фоновая задача. После шага 4 задача полностью описана
данными и не требует ничьих решений.

### Компоненты и переиспользование open-source

| Слой | Готовое | Свой код |
|---|---|---|
| Агенты | LangGraph, LiteLLM | промпты, JSON-схемы ответов, валидация пулов |
| Преобразование в БД | `pgcrypto` (`hmac`), встроенные `jsonb`-функции | SQL-функции стратегий, генерация правил из плана |
| Ввод/вывод | `pg_dump -Fd -j N` / `pg_restore -j N` | обёртка-процесс, стриминг артефактов |
| Ядро и хост | ASP.NET Core Minimal API, Npgsql (binary COPY), Hangfire | оркестрация фаз, материалы, валидация, отчёт |
| Инфраструктура | Docker Compose, Testcontainers, Bogus (демо-данные) | compose-файл, seed-демо |

Сервисы compose: `api` (.NET) · `worker` (.NET) · `agents` (Python/LangGraph) ·
`pg-meta` (состояние задач) · `pg-sandbox` (одноразовая БД с `pgcrypto`) ·
`seed` (демо-данные с фейковыми ПДн).

**Почему не PostgreSQL Anonymizer.** Расширение `anon` рассматривалось как готовый слой
маскирования и отпало: его функции-подделки выдают случайные значения, а требование секции 3 —
стабильность между запусками при том же seed. Использовать `anon` можно было бы только заменив
его генераторы своими, то есть оставив от расширения лишь синтаксис правил, которые у нас и так
описаны планом. От готового берём `pgcrypto`, а правила генерирует ядро.

### Детекторный каталог (шаг 2)

Три независимых сигнала, результат — уверенность `high` / `medium` / `low`:

| Сигнал | Пример |
|---|---|
| Имя колонки | `first_name`, `fname`, `surname`, `email`, `phone`, `passwd`, `salt`, `card_number`, `address`, `inn`, `birth*` |
| Тип и ограничения | `varchar(11)` + unique + цифры → телефон/ИНН; `bytea` / `char(60)` → hash |
| Профиль выборки | доля значений под regex email/phone/Luhn на 1000 строк |

Детекторы — данные (YAML-каталог), не код: добавить `snils` или `passport_number` = строка в каталог.

### Стратегии замены

| Стратегия | Для чего | Источник значений |
|---|---|---|
| `Fake` | ФИО, адреса, названия компаний | пул компонент **от агента (LLM)**, адресация хэшем |
| `Derive` | email/login — производятся от выбранного фейкового имени | пул + шаблон + суффикс |
| `Format` | карта (Luhn), ИНН, телефон, UUID | перестановка домена + шаблон формата из плана; контрольная цифра пересчитывается |
| `Secret` | password_hash, salt, token | хэш известного dev-пароля / перестановка домена |
| `Shift` | даты рождения | оффсет `HMAC(seed, оригинал) mod 2N − N` дней, `N` задан в плане; смещение своё у каждого значения |
| `Redact` | свободный текст, `json` / `jsonb` целиком | подстроки рассказа из репозитория, длина сохраняется |
| `Keep` | всё остальное | — |

Два первых механизма привязки (перестановка домена и адресация пула) описаны в секции 3;
`Shift`, `Secret` и `Redact` домен готовых значений не адресуют, а выводят результат
из оригинала арифметикой или срезом материала.

## Секция 2. Интерфейс ревью (шаг 3)

Три экрана:

- **Jobs** — список задач: источник, статус, длительность, ссылки на дамп и отчёт.
- **Plan review** — слева дерево `схема → таблица`, справа колонки. Строка колонки: имя, тип,
  строк/уникальных, 3 замаскированных примера, предложенный семантический тип
  (`high` — отмечен заранее, `medium` — подсвечен и требует явного решения), выбор стратегии.
  Сверху счётчик «12 из 340 колонок помечены, 3 требуют решения» и кнопка «Заморозить план».
- **Report** — «до/после»: примеры значений, строк по таблицам, уникальных значений до и после,
  результат проверки FK, результат проверки «ни одно исходное чувствительное значение
  не встречается в выходном дампе».

Два обязательных свойства:

1. **План переиспользуется.** На той же схеме подтягивается предыдущий план, показываются только
   диффы (новые, исчезнувшие, сменившие тип колонки). Неразрешённая новая колонка блокирует заморозку —
   это же закрывает риск «новая колонка с ПДн проехала мимо».
2. **Дамп не выгружается, пока план не заморожен.** Для задачи в статусе `AwaitingReview` экспорт недоступен.

## Секция 3. Консистентность и целостность

### Два механизма привязки

Подстановка — чистая функция `(seed, оригинал) → новое значение`. Механизм выбирается
**семантическим типом, а не колонкой**: иначе одна и та же почта в колонке с `unique`
и в колонке без него получила бы разные значения, и сквозность сломалась бы.

| Механизм | Где применяется | Как работает |
|---|---|---|
| **Перестановка домена** (FPE) | фиксированный алфавит: телефон, карта, ИНН, СНИЛС, паспорт, токен, внешний id | снимаем форматирование → остаётся `n` символов алфавита → это число в домене `\|A\|^n` → перестановка домена, задаваемая seed → возвращаем формат |
| **Адресация пула хэшем** | естественный язык: ФИО, адрес, название компании | индекс = `HMAC(seed, normalize(оригинал)) mod \|домен\|`, где домен — произведение пулов компонент от агента |

Свойства, ради которых механизмы разделены:

- FPE — **биекция**, поэтому уникальность гарантирована конструкцией, а проход по `DISTINCT`
  не нужен вовсе. Значение вычисляется из самого оригинала, значит появление новых строк
  не смещает уже выданные значения.
- Для естественного языка FPE бесполезен: перестановка байтов даёт мусор, а не правдоподобное
  имя. Пул даёт правдоподобность, а повторы в нём естественны — живые люди тоже бывают тёзками.

**Ранг в наборе `DISTINCT` не используется нигде.** Он требует состояния (материализованного
порядка) и смещает все значения при любом изменении набора.

### Размер домена пула — параметр замороженного плана

Агент отдаёт **не готовые ФИО, а компоненты**: например 2048 имён × 4096 фамилий × 2048 отчеств,
что даёт ≈1.7·10¹⁰ комбинаций — снова большой домен, только адресуемый хэшем, а не оригиналом.

Размер домена **объявляется в плане и замораживается вместе с ним**. Это не деталь реализации,
а требование корректности: `|домен|` стоит в `mod`, поэтому вывод размера из числа строк означал бы,
что первый же подросший дамп переставляет все значения и межзапусковая стабильность рассыпается.
Агент обязан наполнить ровно объявленный объём; изменение размера — новая версия плана
с явным предупреждением «значения переедут».

### Суффикс уникальности

Пуловое значение дополняется детерминированным суффиксом в base36 от `HMAC(seed, оригинал)`.
**Ширина суффикса — второй явный вход задачи** рядом с seed, печатается в отчёте.

Суффикс включается **на семантический тип автоматически**, если хоть одна колонка этого типа
где-либо в схеме несёт ограничение уникальности. Ручного конфига нет, сквозность цела:
такое ФИО становится «Петров Семён k3f9x2» во всей базе, включая колонки без `unique`.

Почему нельзя просто «заказать пул с запасом»: мешает парадокс дней рождения. При домене
1.7·10¹⁰ и 10 млн уникальных ФИО коллизии не маловероятны, а гарантированы — ожидаемо тысячи.
Раздуть пул до `D >> N²` силами агента невозможно. Суффикс шириной 6 символов добавляет
множитель 36⁶ ≈ 2.2·10⁹, домен становится ≈3.8·10¹⁹, и вероятность коллизии на тех же
10 млн значений падает до ≈1.3·10⁻⁶.

Фаза Verify проверяет дубликаты в каждой unique-колонке. При коллизии лечение —
увеличить ширину суффикса на символ и перезапустить: результат снова детерминирован,
состояния не появляется.

### Email и login

Связность и гарантированная уникальность здесь несовместимы: связность означает, что локальная
часть выводится из фейкового ФИО, то есть отображение перестаёт быть биекцией домена,
а без биекции гарантию уникальности даёт только знание занятых значений, то есть состояние.

Выбрана связность: `petrov.semyon.k3f9x2@mail.invalid` — локальная часть из того же фейкового ФИО
плюс суффикс той же ширины-параметра. Разработчик видит в dev-базе, что почта и имя принадлежат
одному человеку. Уникальность вероятностная, страхует та же проверка дубликатов в Verify.

Домен во всех случаях заменяется на **неотправляемый** (`@mail.invalid`), чтобы из dev-контура
нельзя было написать живому человеку.

### FK на натуральных ключах

Согласованность значений по обе стороны ссылки бесплатна: подстановка — чистая функция
от `(seed, оригинал)`, поэтому `users.email` и `orders.user_email` превращаются в одно и то же
новое значение. Проблема только механическая — FK проверяется по ходу `UPDATE`,
и промежуточное состояние ссылку рвёт.

Решение: **снять FK-ограничения в sandbox перед Apply, обновить таблицы независимо
и параллельно, затем восстановить исходные определения.** Валидация при пересоздании и есть
проверка ссылочной целостности из фазы Verify, поэтому полный скан — не лишняя работа,
а требуемый артефакт отчёта. Вариант с `SET CONSTRAINTS ALL DEFERRED` отвергнут: он требует
уложить весь Apply в одну транзакцию на все таблицы, что на больших объёмах даёт раздутые WAL
и долгие блокировки.

### json / jsonb

По умолчанию колонка обрабатывается **целиком стратегией `Redact`**: структура, ключи и типы
скаляров сохраняются, строковые значения заменяются текстом той же длины. Числа и булевы значения
остаются как есть — заменить их текстом нельзя, не сломав тип; если внутри `payload` лежит
чувствительное число, путь размечается вручную. Дефолт безопасный — строковые ПДн внутри
`payload` не уедут в дамп из-за того, что путь пропустили при ревью.

В ревью колонку можно раскрыть в дерево путей и разметить важные. Профилировщик рекурсивно
обходит выборку (`jsonb_each`) и собирает встречающиеся пути со скалярными значениями;
размеченный путь получает семантический тип и стратегию наравне с колонкой таблицы, замена —
через `jsonb_set`. Так `payload->'customer'->>'phone'` совпадёт с колонкой `phone`,
а `status` останется `paid`. Неразмеченные пути остаются под `Redact`.
Новый путь, как и новая колонка, блокирует заморозку плана.

### Свободный текст

В текстовых колонках заменяется то, что надёжно ловится регуляркой — email, телефон, карта,
ИНН, СНИЛС — и заменяется **теми же чистыми функциями**. Поэтому телефон, упомянутый
в комментарии, превращается в тот же самый фейковый телефон, что и в колонке `phone`:
сквозность держится и в прозе.

Имена в свободном тексте regex не находит. Это признаётся вслух: колонка помечается в отчёте
как остаточный риск, и человек в ревью может выбрать `Redact`. Вариант со словарём известных
значений (собрать `DISTINCT` из чувствительных колонок и искать вхождения) отвергнут: он
возвращает состояние и не масштабируется — поиск миллионов терминов в миллионах строк
квадратичен. Вариант «прогнать текст через LLM» отвергнут принятым решением о роли агентов:
LLM не участвует в обработке строк.

### Redact — генератор текста из рассказа

К репозиторию прикладывается текст рассказа; он и служит источником замен. Без LLM,
детерминированно, длина сохраняется — значит вёрстка и парсеры в dev ведут себя как в проде.

- Смещение в рассказе = `HMAC(seed, оригинал) mod длина рассказа`, поэтому замена остаётся
  чистой функцией и воспроизводится по seed.
- Поле длиннее рассказа — рассказ повторяется по кругу.
- Значение из одного слова — берётся случайное слово той же длины из рассказа;
  если слова нужной длины нет, падаем на подстроку.

### Отчёт живёт в контуре плана

Раз seed попадает в отчёт, отчёт по чувствительности равен таблице соответствий: имея seed
и пул, можно проверять догадки об оригиналах. Значит отчёт имеет тот же уровень доступа,
что и план, и не является артефактом «можно переслать куда угодно».

## Секция 4. Масштабируемость

### Граница .NET / SQL

Разделение проходит не по стратегиям, а по типу работы — и именно это убирает риск двух
реализаций одного преобразования.

**.NET, один раз на задачу, объём работы O(размер пула):** валидирует ответ агента и загружает
в sandbox таблицы-материалы — компоненты пулов, текст рассказа, индекс слов рассказа по длине,
алфавит суффикса, форматные шаблоны из плана. Хэш материалов пишется в план.

**SQL, на строку, set-based:** `hmac` из pgcrypto и арифметика дают индекс или перестановку
домена, дальше идёт выбор готового материала и конкатенация.

Правило границы: **правдоподобные строки — те, что человек читает как имя, адрес или текст —
строятся только в .NET; СУБД их адресует, режет и склеивает, но не изобретает.** Арифметические
величины (цифры телефона после перестановки, base36-суффикс) остаются в SQL: они выводятся
из числа однозначно, второй реализации у них не бывает. В результате расхождение «одно исходное
значение дало разные результаты в двух колонках» исключено конструктивно, а не договорённостью.

### Apply — пересборка таблицы с подменой, не UPDATE

FK уже сняты (секция 3), индексы всё равно пересоздаются, поэтому `UPDATE` не даёт ничего,
кроме мёртвых кортежей и раздутых индексов. Вместо него:

```
CREATE TABLE t_new AS SELECT <преобразование> FROM t
  ─► индексы и ограничения строятся один раз, параллельно
  ─► Verify: JOIN t и t_new по размеченным колонкам
  ─► DROP TABLE t; ALTER TABLE t_new RENAME TO t
  ─► возврат FK
```

**Verify встаёт между сборкой и подменой** — именно там, где старая таблица ещё жива, и потому
сравнение «до/после» делается обычным `JOIN`, без отдельного снапшота оригиналов.

Порог по размеру не вводим: через тот же путь идёт любая таблица с размеченными колонками.
На маленькой таблице выигрыша нет, зато нет и второго пути исполнения — а главное, проверка
«исходные значения не утекли» требует живого оригинала, и `UPDATE` его затирает.

Таблица создаётся **логированной**: `UNLOGGED` даёт ту же скорость, но попадает в DDL выходного
дампа, и схема перестаёт совпадать с продовой. Скорость обеспечивается настройками одноразовой
`pg-sandbox` — `fsync=off`, `synchronous_commit=off`, `full_page_writes=off`, `wal_level=minimal`;
при `wal_level=minimal` наполнение только что созданной таблицы в той же транзакции WAL почти
не пишет. Потеря данных при сбое здесь ничего не стоит — дамп перезаливается.

### Параллелизм

По таблицам — пул воркеров по числу ядер; порядок не важен, так как FK сняты. Внутри таблицы
`CTAS` параллелится самой СУБД, поэтому явный чанкинг по диапазонам PK нужен только для прогресса
и рестарта на таблицах выше порога. Ввод-вывод — `pg_restore -j N` и `pg_dump -Fd -j N`
(параллельная выгрузка работает только с форматом каталога `-Fd`).

### Стоимость LLM

Обращений O(число семантических типов), не O(число строк). Пул кэшируется в `pg-meta` по ключу
«семантический тип + объявленный размер домена + версия промпта» и фризится вместе с планом
по хэшу. Это не только экономия: индекс `HMAC mod |домен|` адресует конкретное содержимое пула,
поэтому перегенерация пула другой моделью при том же seed дала бы другие ФИО и сломала
межзапусковую стабильность. Повторный прогон на том же плане к LLM не обращается вовсе.

### Verify как побочный продукт, а не отдельный проход

| Проверка | Откуда берётся |
|---|---|
| Ссылочная целостность | валидация при пересоздании FK |
| Дубликаты в unique-колонках | валидация при пересоздании unique-индекса |
| Количество строк | `count(*)` до и после |
| Разнообразие значений | `count(distinct)` до и после, допуск задан в плане |
| Исходные значения не утекли | `JOIN` старой и новой таблицы по каждой размеченной колонке — полный, не выборочный, пока старая таблица жива |

Три проверки из пяти бесплатны: это валидация ограничений, которую мы обязаны выполнить в любом случае.

## Секция 5. Тестирование и расширяемость

### Расширяемость: sandbox Postgres — движок, а не только приёмник дампа

Требование «расширяемость на другие форматы без переписывания ядра» закрывается тем, что ядро
работает с одной вещью — таблицами в `pg-sandbox`. Значит формат живёт только на краях конвейера.

| Слой | Контракт | Что знает о формате |
|---|---|---|
| `ISourceAdapter` | формат → таблицы в sandbox + каталог схемы | всё |
| Ядро: детекторы, план, mapping, Apply, Verify | таблицы sandbox → таблицы sandbox | ничего |
| `ISinkAdapter` | таблицы sandbox → формат | всё |

Добавить MySQL, CSV или XML — это пара адаптеров, а не правка ядра. Детекторы тоже не трогаются:
они смотрят на метаданные таблиц sandbox и профиль выборки, то есть на нормализованное
представление, а не на исходный формат.

**Живая БД как источник** укладывается в тот же контракт: адаптер сам снимает дамп по переданной
строке подключения, дальше задача идёт как с файлом. В источник не пишем никогда; в документации —
требование выдавать read-only роль и целиться в реплику, а не в мастер.

### Тестирование

**Свойства чистых функций — property-based (FsCheck) против Testcontainers-Postgres.** Функции
живут в SQL, поэтому и тесты идут через СУБД: держать эталонную реализацию на C# «только для
тестов» нельзя — это ровно та вторая реализация, которую запрещает граница из секции 4.
Проверяемые свойства:

- перестановка домена инъективна на выборке и обратима;
- `f(seed, x)` детерминирована — два вызова дают одно значение;
- `Redact` сохраняет длину значения и структуру `jsonb`;
- суффикс включён ровно для тех семантических типов, у которых есть unique-колонка.

**Интеграционный прогон** на демо-схеме из сервиса `seed`: весь конвейер в Testcontainers,
все пять проверок фазы Verify, снапшот «до/после» как артефакт для демонстрации.

**Тест воспроизводимости.** Два прогона с одним seed дают одинаковый результат. Сравнение
не побайтовое: `pg_dump` не гарантирует порядок строк, поэтому сверяем
`md5(string_agg(колонка ORDER BY pk))` по каждой размеченной колонке.

**Тест роста данных — главный для требования стабильности.** Прогон, затем в источник добавляются
строки, затем повторный прогон с тем же seed и тем же планом: значения, существовавшие в первом
прогоне, обязаны совпасть. Именно этот тест ловит любое случайное возвращение ранга по `DISTINCT`
или вывод `|домен|` из числа строк.

**Регрессия каталога детекторов.** Каталог — данные, поэтому на фикстуре схемы проверяется
ожидаемый набор кандидатов с уверенностями. Добавление `snils` в YAML не должно менять вердикты
по остальным колонкам.
